2. PARANCS-TÁBLA FELÉPÍTÉSE
================================================================================

Helye:       0x08B20 – 0x0AF80 a CPU-order képben
Bejegyzések: 388 db, egyenként 24 byte

Rekord formátum (24 byte):
  [00–01] name_len    — parancs neve hossza (max 10 karakter)
  [02–11] name        — 10 byte, null-padded
  [12–13] cmd_id      — belső opcode
  [14–15] flags       — REV9-ben mindig 0x0000
  [16–17] 0x89EA      — dispatch engine konstans
  [18–19] handler_hi  — handler cím HIGH szó (tipikusan 0x0001)
  [20–21] handler_lo  — handler cím LOW szó
  [22–23] priv        — hozzáférési szint

FONTOS: A VALÓDI handler-cím = (handler_hi << 16) | handler_lo
        Tehát handler_lo=0x7BBA + handler_hi=0x0001 → 0x00017BBA
        Ez a 24-bites ROM-cím a tényleges 68000 rutin belépési pontja.

Flag2 (handler_hi) értékek:
  0x0000 = token/keyword (nincs handler; flag2 és handler_lo is 0x0000)
  0x0001 = normál parancs (handler_hi = 0x0001, handler = 0x00017xxx)
  0x0002 = query parancs
  stb.

Priv mező:
  0x0000 = korlátlan
  0x0001 = standard (legtöbb parancs)
  0x0002 = CIIL option szükséges
  0x0003 = legmagasabb privilégium

5. MADDR / MREAD / MWRITE — MEMÓRIA-HOZZÁFÉRÉS GPIB-EN
================================================================================

FONTOS ELŐFELTÉTELEK:
  1. BEEP 1  →  engedélyezi az MREAD-et (A5+0x13A6 = 1)
  2. BEEP 2  →  MREAD direkten, security check NÉLKÜL (bypass!)
  3. Alternatíva: MREAD a "BEEP 2" aliasán keresztül mindig működik

--- MADDR (cím beállítása) ---

Szintaxis:  MADDR <decimal_address>
Példák:
  MADDR 9200       ← 0x23F0 decimálisan = 9200
  MADDR 73728      ← 0x12000 = 73728 (RAM terület kezdete kb.)
  MADDR 1179648    ← 0x120000 = 1 179 648

FIGYELEM:
  - Cím DECIMÁLISAN adandó meg (NEM hexában!)
  - Belső float konverzió: 9200 → IEEE 754 double → deszkriptor
  - Az int_to_ieee754 (0x583BA) és ieee754_to_int (0x58340) rutinok végzik

--- MREAD (memória olvasás) ---

Szintaxis:  MREAD
Feltétel:   BEEP 1 előbb (vagy BEEP 2 = közvetlen bypass)

Amit csinál (0x00017BBA handler):
  1. Veszi az MADDR deszkriptorát
  2. ieee754_to_int (0x585A0 → 0x58340): float → integer RAM-cím
  3. Páros-igazítás (ANDI.L #$FFFFFFFE): word-boundary
  4. MOVE.W (A0), -(A7): WORD (2 bájt!) olvasás az adott cím ről
  5. gpib_send_word (0x1D8DC → 0x50958): decimális ASCII → GPIB
  6. Eredmény formátuma: "+XXXXX" vagy "-XXXXX" (max 5 decimális jegy)

Visszatérési érték példák:
  MREAD → "+2345"    (ha a cím  tartalma 0x0929 = 2345)
  MREAD → "-1"       (ha 0xFFFF = -1 signed)
  MREAD → "+0"       (ha 0x0000)

--- MWRITE (memória írás) ---

Szintaxis:  MWRITE <decimal_value>
Feltétel:   SECURE kód + A5+0x144A flag megfelelő állapot

Amit csinál (0x00017BF6 handler):
  1. Veszi a value paramétert ($8(A6))
  2. Veszi az MADDR deszkriptort ($A(A6))
  3. ieee754_to_int: float descriptor → integer target address
  4. MOVE.W $8(A6), (A0): WORD (2 bájt!) írás a célcím re

MWRITE mindig WORD írást végez (2 bájt)!

--- JSR GPIB-PARANCS (kódvégrehajtás) ---

Szintaxis:  JSR <decimal_address>
VESZÉLYES: Tetszőleges 68000 kódot futtat a megadott ROM-cím en!

Amit csinál (0x00017C28 handler):
  1. ieee754_to_int: float → integer address
  2. JSR (A0): meghívja a 68000 kódot ezen a cím en

Csak ROM-beli rutinokra biztonságos! Ismeretlen cím re soha!

--- CALLARRAY ---

Szintaxis:  CALLARRAY <array_ptr>, <index>
Handler:    0x00017C58

Vtable-alapú metódushívás:
  A0 = array base, D0 = index
  A2 = dereference array[index] (pointer a descriptor-ra)
  A3 = dereference A2+0x16 (vtable method pointer)
  JSR (A3): meghívja a metódust

--- Példa munkamenet (Python pyvisa) ---

import pyvisa
rm   = pyvisa.ResourceManager()
inst = rm.open_resource('GPIB::22::INSTR')
inst.timeout = 5000

# BEEP engedélyezés (MREAD gate)
inst.write('BEEP 1')

# MADDR: 0x120000 = 1179648 decimális
inst.write('MADDR 1179648')
val = inst.query('MREAD')
print(f'Érték: {val}')

# CAL RAM dump (word-onként, 256 word = 512 bájt)
results = []
for i in range(256):
    cim = 1179648 + i * 2          # word-onként léptetünk
    inst.write(f'MADDR {cim}')
    v = inst.query('MREAD').strip()
    results.append((cim, int(v)))
    print(f'0x{cim:08X}: {v}')

# BEEP 2 bypass (nincs szükség előzetes BEEP 1-re):
inst.write('MADDR 9200')
val = inst.query('BEEP 2')   # VAGY:
val = inst.write('BEEP 2'); val = inst.read()

Factory kód: 22 (közismert HP szerviz-kód)

  ≠0 = szabad (MREAD aktív)
  = 0 = védett (MREAD IG NORED)

AJÁNLOTT SORREND (egyre kockázatosabb):

1. CSAK LEKÉRDEZÉS (teljesen biztonságos):

   BOMB?         → self-test query

     * Fizikai NVRAM chip (DS1220/FRAM) mentve és jelölve

     * Min. 3 egyező dump, hash ellenőrizve
     * Eredeti chip félretéve
   Eljárás:
     SECURE 22     → védelmi kód
     MADDR <cim>   → célcím
     MWRITE <val>  → WORD írás (2 bájt!)

     - CAL konstansokat tesztelés nélkül
     - Ismeretlen cím ekre
     - Ellenőrizetlen értékeket

   JSR <cim>     → 68000 kód végrehajtás GPIB-ből

   Pl. JSR <REV? handler cím> = REV? aliasa

  CRASH_  (reset!)
  MWRITE CAL területre
  CAL, STORE, SAVE, INIT, ERASE, FORMAT
  JSR ismeretlen cím re

12. [ÚJ] HANDLER-CÍM KONVENCIÓ ÉS BELSŐ ARCHITEKTÚRA
================================================================================

A parancs-tábla rekordjaiban [18-21] mezők adják a 32-bites handler-cím et:
  bytes [18-19] = handler_hi  (tipikusan 0x0001)
  bytes [20-21] = handler_lo  (pl. 0x7BBA)
  → Valódi 24-bit cím: 0x00017BBA

Ez a cím  tartalmaz 68000 LINK utasítással kezdődő rutin belépési pontot.

A kétszintes cím -rendszer oka: a BEEP dispatch kódjában a "0x7xxx" tartomány
szintén tartalmaz MREAD-hez kapcsolódó rutinokat, de ezek a beágyazott
"BEEP flag" kapuőrhöz kapcsolódó wrapper-ek, nem a tényleges handlerek.

Handler-cím  helyes vs. hibás értelmezés:
  Helytelen: handler = handler_lo = 0x7BBA  →  BEEP wrapper-ben landol
  Helyes:    handler = 0x00017BBA           →  valódi MREAD rutin (LINK A6, #-12)

CALLARRAY vtable-mechanizmusa:
  descriptor[0x16] = method pointer  (vtable-szerű objektum-interfész)
  A 68000-ben nincs natív OOP, de a HP mérnökök implementálták!

13. [ÚJ] BEEP ↔ MREAD KAPCSOLAT (BIZTONSÁGI KAPUŐR)
================================================================================

A HP3458A biztonsági architektúrájában a BEEP parancs kettős szerepet tölt be:

BEEP handler (0x7BCC) kódrészlete:
  LINK A6, #0
  MOVE.W $8(A6), D7        ← BEEP mode (0/1/2/-1)
  BRA.B $7C1E              ← mode dispatch

  ; D7=0 vagy D7=1 esetén (0x7BD6):
  MOVE.W $8(A6), D0        ← D0 = mode
  MOVE.B D0, $1DB5(A5)     ← tárolja A5+0x1DB5-be
  MOVE.B D0, $13A6(A5)     ← UGYANODA TÁROLJA: A5+0x13A6 = MREAD gate!
  JSR $5DA0C               ← hardver beeper vezérlés

MREAD entry (0x7BBA) kódrészlete:
  TST.B $13A6(A5)          ← ellenőrzi a BEEP flag-et
  BEQ.B $7BC8              ← ha 0 (BEEP OFF): SKIP → nem olvas semmit!
  JSR $763A                ← ha ≠0 (BEEP ON): MREAD fő logika

BEEP mode hatása:
  BEEP 0  → A5+0x13A6 = 0  → MREAD TILTOTT (üres visszatérés)
  BEEP 1  → A5+0x13A6 = 1  → MREAD ENGEDÉLYEZETT
  BEEP 2  → közvetlenül JSR 0x763A → MREAD bypass (security check kihagyva!)
  BEEP -1 → hiba ("Expected 0 to 2 or -1 for mode" @ 0x84D4)

KÖVETKEZMÉNY: Alapbeállításban a BEEP állapota dönti el, hogy MREAD működik-e.
  Ha a műszer BEEP-je ki van kapcsolva → MREAD is tiltott.
  Megoldás: BEEP 1 először, vagy BEEP 2 direkt (bypass).

14. [ÚJ] FLOAT DESZKRIPTOR RENDSZER (IEEE 754)
================================================================================

A HP3458A GPIB BASIC interpretere MINDEN értéket 8-bájtos
IEEE 754 double-precision floating point-ként kezel.

Ez vonatkozik a memória-cím ekre is!

MADDR <decimal> → belső konverzió:
  1. "9200" string → 9200.0 double → 8-bájtos deszkriptor
  2. Deszkriptor RAM-ban tárolva (mint MADDR változója)

MREAD → cím feloldás:
  1. 8-bájtos deszkriptor betöltés
  2. descriptor_to_addr (0x585A0) → ieee754_to_int (0x58340)
  3. IEEE 754 double → integer:
     - Exponent kinyerés: (D0 & 0x7FF0) >> 4 → biased exp
     - Bias korrekció: exp - 0x3FE (= 1022, standard 1023-as + 1 offset)
     - Mantissa + sign rekonstrukció
  4. ANDI.L #$FFFFFFFE: páros-ra igazítás (WORD access miatt)
  5. Eredmény: a tényleges CPU RAM-cím  D7-ben

Deszkriptor struktúra (8 byte, param pointer által mutatva):
  [0x00-0x07]: IEEE 754 double value
  [0x0C]:      típusjelző (ha == 0x0004: közvetlen érték, nem pointer)
  [0x0E]:      hozzáférési típus / D7 dispatch érték (1/2/3/4)
  [0x16]:      tényleges cím  vagy pointer a cím hez

MADDR dispatch (0x17D04), D7 értéke alapján:
  D7=1 → 0x17C9A → tipus-1 leíró kezelés
  D7=2 → 0x17CC0 → tipus-2 leíró kezelés
  D7=3 → 0x17CE6 → tipus-3 leíró kezelés
  D7=4 → 0x17CF2 → tipus-4 leíró kezelés

Cím -konverziós rutinok:
  0x585A0 = descriptor_to_addr  (deszkriptor → int, MREAD/MWRITE/JSR használja)
  0x58340 = ieee754_to_int      (IEEE 754 double → 32-bit int, mag)
  0x583BA = int_to_ieee754      (32-bit int → IEEE 754 double)
  0x585B4 = store_descriptor    (int → deszkriptor visszatárolás)

15. [ÚJ] pSOS RTOS RENDSZERHÍVÁSOK
================================================================================

A HP3458A pSOS (Process Schedulable OS) valós idejű OS-t futtat.
Megerősítő szöveg: "N^NuFATAL PSOS ERROR IN SPAWN_P" @ 0x001DEC

pSOS rendszerhívás interfész:
  moveq  #<sysnum>, d7    ← rendszerhívás száma D7-ben
  trap   #0               ← TRAP #0 = pSOS szoftver-megszakítás

pSOS rendszerhívás #24 (0x18) — GPIB I/O csatorna:
  Kód: moveq #$18, d7; trap #0
  Paraméterek:
    A0 = csatorna descriptor (A5+0x0F00 = GPIB output csatorna)
    A1 = output buffer (A5+0x120C6E)
    D0 = buffer offset/méret
    D1 = flags

A pSOS csatornák belső tábláiban:
  0x120C14 = referencia-számláló tábla (típusonként egy word)
  0x120C32 = pointer tábla (típusonként egy long ptr)
  0x120C6E = output buffer

MREAD szempontjából:
  JSR $188C8 → TRAP #0 (pSOS I/O) → olvassa a MADDR-értéket és előkészíti
  JSR $49DE  → küldési rutin → GPIB-re megy az eredmény
